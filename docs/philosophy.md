# 设计哲学：为什么是"框架"而非"替身"

> 本文回答一个问题：当你说"用巴菲特的框架看看这家公司"时，仓库里究竟发生了什么？
> 它不是"请巴菲特来回答问题"，而是"把巴菲特做判断时用的那套检查动作，摊开成你能自己走一遍的流程"。

---

## 一句话立场

**本仓库交付的是可拆解、可检查、可反驳的思维工具，不是人格替身。**

每一位专家对应一份 `skills/<slug>/` 目录，其中固化的是他的**判断框架、检查清单、观点年表、失效场景**，而不是他的口吻、立场和结论。你拿到的是"他的方法"，不是"他的答案"。

---

## 三条否定：这个仓库不做什么

| 不做 | 具体含义 | 为什么不做 |
|------|---------|-----------|
| **不模拟人格对话** | 不做"我是巴菲特，你好孩子"这类角色扮演式应答 | 角色扮演会奖励"像不像"，而不是"对不对"；判断质量无法被检查 |
| **不冒充本人** | 每个 SKILL.md 的 frontmatter 与正文均显式声明不声称代表本人，见下文"边界声明" | 已故或在世名人都无法为本仓库的输出背书，冒充即失真 |
| **不产出"某人会怎么说"的具体结论** | 不预测本人的即期观点，不编造未公开研究 | 一旦输出被当成"本人观点"传播，错误的责任无法归属 |

这三条不是法律免责话术，而是设计约束：它们决定了 `references/` 里能写什么、不能写什么。

---

## 三条肯定：这个仓库做什么

| 做 | 落到哪个文件 |
|----|------------|
| **提供可拆解的判断框架** | `references/01-core-theories.md`、`02-analysis-frameworks.md` |
| **提供可检查的动作清单** | `references/07-checklist.md`——判断前该看什么、按什么顺序看 |
| **提供可追溯的观点年表** | `references/04-key-views-timeline.md`——某人何时说过什么、后来被验证还是被证伪 |
| **提供失效场景（反例库）** | `references/08-style-anti-patterns.md`——这套框架在什么情况下会错 |

一个关键取舍：**正反双校验**。只写"他怎么做对"的框架是宣传册，写清"他什么时候做错"的框架才是工具。因此每位专家的 `references/` 固定 8 个编号文件，其中 `07`（清单）与 `08`（反例）构成一对——前者防止你漏看，后者防止你迷信。

```
skills/<slug>/references/
├── 01-core-theories.md          核心理论与概念
├── 02-analysis-frameworks.md    分析框架与推演路径
├── 03-style-and-voice.md        文风与表达特征
├── 04-key-views-timeline.md     观点年表
├── 05-publications.md           著作与公开材料
├── 06-glossary.md               术语表
├── 07-checklist.md              判断前检查清单  ← 防漏看
└── 08-style-anti-patterns.md    反例库（失效场景）← 防迷信
```

---

## "文风"为什么保留，但不等于扮演

`references/03-style-and-voice.md` 存在，是因为**表达方式本身承载判断信息**：格林斯潘式的模糊措辞、芒格式的逆向提问、利弗莫尔式的"关键点"叙事，都是方法的一部分，剥掉它们框架会变形。

但文风是有边界的：

- 文风用于**让推导过程更贴近该方法本来的思维方式**，而不是用于生成"像本人说话"的内容；
- 文风不得用于**伪装身份**——输出里不应出现第一人称的本人自述；
- 一旦文风与判断冲突，**判断优先**。宁可写得不像，也不能为了像而牺牲准确性。

## 圆桌：为什么是"按需组阁"而非预设套餐

一个常见做法是把专家打包成"宏观智囊团""价值投资团"若干固定组合，用户点选即可。本仓库**刻意不走这条路**，理由有三：

1. **预设套餐隐含了"问题已被正确分类"的假设。** 真实问题往往跨域（"美联储降息对 A 股意味着什么"同时涉及全球宏观、中国流动性与微观估值），强行塞进一个套餐会系统性漏掉关键视角。
2. **固定组合会随时间腐化。** 专家池从 36 人扩到 51 人，预设套餐只会在每次扩容后变得过时，且没人负责重排。
3. **组阁过程本身是有信息的。** "为什么这次请了洪灏而不是付鹏"这件事，应该由问题的标签命中决定并可被复现，而不是由某个组合文件的作者拍定。

因此本仓库的圆桌是**动态组装**：

> 不是"你要用宏观智囊团"，而是"你的问题涉及中美宏观 + 微观估值，所以帮你组一个圆桌：`gao-shanwen`（中国宏观）+ `greenspan`（全球宏观）+ `warren-buffett`（估值）"。

具体算法（两级命中、阶段限额、兜底规则、列席上限）与可执行脚本，见 [智囊团组合指南](combination-guide.md)。

## 与"人格化 Skill"的差异

市面上另一种做法是"人物陪聊/数字分身"：模拟语气、模拟经历、模拟情绪反应。两者目标不同，不存在优劣，但选型时容易混淆，故并列如下：

| 维度 | 本仓库（框架派） | 人格化 / 数字分身（替身派） |
|------|----------------|--------------------------|
| 核心产物 | 判断流程、检查清单、失效场景 | 人格设定、对话风格、情绪反应 |
| 成功标准 | 推导可被复现、结论可被反驳 | 交互自然、像不像本人 |
| 对"本人"的关系 | 引用公开方法与公开观点，明确不代言 | 声称延续或还原本人 |
| 出错时的责任 | 框架适用边界写清在 `08` 反例库 | 容易把框架缺陷归因于"人格演得不像" |
| 适合的场景 | 投研、决策复盘、方案互检 | 陪伴、内容创作、角色体验 |

一句话：**替身派优化"像"，框架派优化"对"。** 本仓库只做后者。

## 边界声明

每个 `SKILL.md` 的 frontmatter `description` 均含固定句式"不声称代表…本人或其未公开观点"；正文在 `## 何时使用` 之前另有一行说明，逐字如下（以 `warren-buffett` 为例）：

```
> 说明：本技能是**思维框架与文风的工具**，用于辅助用户自行研判。它不声称代表 沃伦·巴菲特 本人，也不引用或复制任何未公开的专有研究。所有数据判断应以实时信息为准。
```

这段文字由 `tools/skill-gen/build.py` 统一渲染，不依赖人工维护，因此 51 份 SKILL.md 的表述逐字一致（仅人名不同），也不会在扩容时被遗忘。可自行核验：

```bash
# 排除 _template 后统计模板种类：期望输出「不同模板数: 1 | 覆盖 skill 数: 51」
python -c "
import os,re,collections
c=collections.Counter()
for d in sorted(os.listdir('skills')):
    p=os.path.join('skills',d,'SKILL.md')
    if not os.path.exists(p) or d=='_template': continue
    for line in open(p,encoding='utf-8'):
        if line.startswith('> 说明：本技能是'):
            c[re.sub(r'不声称代表 .*? 本人','<NAME>',line.rstrip())]+=1
print('不同模板数:', len(c), '| 覆盖 skill 数:', sum(c.values()))
"
```

`skills/_template/` 是唯一的例外——它保留占位符 `<人物>` 与 `<如有逝世等补充信息>`，供新增人物时填充（当前 51 份正式 skill 中该补充位均为空，未使用），不计入上表的 51 份。

**必须被理解的三层含义**：

1. **不代表本人**——输出不是任何名人的观点，不得被引用为"某某说"；
2. **不引用未公开研究**——只使用公开著作、公开访谈、公开演讲中的方法；
3. **数据以实时信息为准**——框架给的是"该看什么、怎么推"，不是"现在的数值是多少"。任何具体数字都必须由使用者在当下自行核实。
